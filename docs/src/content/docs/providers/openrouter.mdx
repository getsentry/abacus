Abacus tracks OpenRouter usage by reading daily activity for each provisioned key via the [OpenRouter Management API](https://openrouter.ai/docs/api-reference/management). Usage is attributed to team members by matching provisioned-key hashes to email addresses stored in the `openrouter_keys` table.

## Setup

<Steps>

1. Open [OpenRouter → Settings → Keys](https://openrouter.ai/settings/keys) and generate a **Management API key** (starts with `sk-or-v1-`) for each workspace you want to track.

2. Set the environment variable. Use the single-key form for one workspace, or the JSON map for multiple:

   **Single workspace:**
   ```bash
   OPENROUTER_MANAGEMENT_KEY=sk-or-v1-...
   ```

   **Multiple workspaces:**
   ```bash
   OPENROUTER_MANAGEMENT_KEYS='{"Coding Agents":"sk-or-v1-...","Tools":"sk-or-v1-..."}'
   ```

   See [Multi-Workspace Configuration](#multi-workspace-configuration) for details.

3. Provision API keys for each team member via the OpenRouter API or dashboard. Abacus records each key's hash and associates it with a user email — see [provisioning documentation](/abacus/providers/openrouter/#key-provisioning).

</Steps>

## Sync Behavior

| Setting | Value |
|---------|-------|
| Schedule | Daily at 00:30 UTC |
| History window | Last 30 days (API limitation) |
| Data freshness | Completed UTC days only — the current day appears after UTC midnight |
| Data | Input tokens, output tokens, cost (USD credits) |
| Attribution | Provisioned-key hash → email mapping |
| Cache tokens | Not available (OpenRouter API limitation) |
| BYOK usage | Not tracked (only usage billed through OpenRouter) |

<Aside type="note">
  The OpenRouter Management API only exposes usage for the last 30 days, and only for **completed UTC days** — the current day's usage is visible on the OpenRouter dashboard immediately but does not appear in the activity API (or Abacus) until the UTC day rolls over. For historical data beyond the 30-day window, the data is simply unavailable — there is no extended archive. Run a one-time CLI backfill promptly after setup to capture the full available window.
</Aside>

## Manual Sync

Sync the last N days of usage data:

```bash
pnpm cli sync openrouter --days 30
```

Check sync status:

```bash
pnpm cli openrouter:status
```

## Backfill Historical Data

OpenRouter backfill always fetches the full available 30-day window — no date range flags are needed or supported (unlike Anthropic/Cursor):

```bash
pnpm cli backfill openrouter
```

Mark backfill as complete (prevents cron from re-running the full window):

```bash
pnpm cli backfill:complete openrouter
```

Reset to allow re-backfilling:

```bash
pnpm cli backfill:reset openrouter
```

## Multi-Workspace Configuration

Abacus supports tracking usage across multiple OpenRouter workspaces. Each workspace maps to one management key; the workspace name is a display label used for segmentation in reports and the UI.

### Environment Variable

Set `OPENROUTER_MANAGEMENT_KEYS` as a JSON object mapping workspace names to management keys:

```bash
# In .env/.env.local — single-quote the JSON to avoid shell interpretation:
OPENROUTER_MANAGEMENT_KEYS='{"Coding Agents":"sk-or-v1-...","Tools":"sk-or-v1-..."}'
```

In the **Vercel environment variable UI**, paste the raw JSON without surrounding shell quotes:

```
{"Coding Agents":"sk-or-v1-...","Tools":"sk-or-v1-..."}
```

### Single-Key Fallback

The original `OPENROUTER_MANAGEMENT_KEY` variable is still fully supported. When set alone it creates a single workspace named `default`. When both variables are present, `OPENROUTER_MANAGEMENT_KEYS` takes precedence.

### Migration Note for Existing Deployments

<Aside type="caution">
  Migration 0019 backfilled all existing key rows and usage records to workspace `'Coding Agents'`. If your deployment previously used `OPENROUTER_MANAGEMENT_KEY`, you must switch to the multi-workspace form with the same workspace name:

  ```bash
  OPENROUTER_MANAGEMENT_KEYS='{"Coding Agents":"sk-or-v1-..."}'
  ```

  Keeping `OPENROUTER_MANAGEMENT_KEY` alone will result in a `default` workspace that does not match the backfilled `Coding Agents` records, causing errors when operating on those rows.
</Aside>

### UI Behavior

The workspace selector and workspace column in the key management UI are only shown when two or more workspaces are configured. With a single workspace the interface is identical to the previous single-key experience.

## Key Provisioning

Abacus attributes usage to team members via provisioned-key hash mapping. When a user is provisioned an OpenRouter API key:

1. The key hash is stored in the `openrouter_keys` table alongside the user's email.
2. During sync, daily activity per key is fetched from the Management API and matched by hash.
3. Usage is recorded under the user's email in the aggregated reports.

<Aside type="tip">
  If a provisioned key is later revoked, Abacus retains the hash → email mapping and will continue to attribute any remaining historical data for that key correctly.
</Aside>

## Cost Semantics

Costs are reported in **USD credits** as returned by the OpenRouter API. This reflects actual billed usage through OpenRouter's platform. Bring-your-own-key (BYOK) usage that bypasses OpenRouter billing is **not** tracked.
